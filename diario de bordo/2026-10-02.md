## Problema de Orquestracao Identificado

O problema principal nao foi incapacidade do NVIDIA TAO de executar jobs. O
problema foi a dependencia de uma sessao do LLM para fazer polling continuo.

A sequencia observada nos eventos OpenCode foi:

1. O modelo validou o contexto.
2. Submeteu o treinamento real corretamente.
3. Consultou o job duas vezes.
4. Consultou logs duas vezes.
5. Descreveu que continuaria monitorando.
6. Encerrou a sessao com `step_finish reason=stop`.

A sessao terminou enquanto o job TAO estava `Started`. Portanto, o modelo nao
falhou ao submeter o job; ele falhou como mecanismo confiavel de espera longa.

Consequencias:

- O relatorio inicial podia parecer bem-sucedido porque o processo OpenCode
  terminou com exit code `0`.
- O pipeline real ainda nao tinha terminado.
- O workflow publicou o relatorio intermediario por usar uma condicao de
  publicacao com `always()`.
- O pipeline de treino pode continuar no TAO mesmo depois de o runner concluir.
- Um novo push podia cancelar o workflow sem cancelar automaticamente o job TAO.

## Falhas do Workflow

O workflow `36966018537` terminou como `failure`, mas o job OpenCode e o job de
publicacao Wiki terminaram com sucesso.

Falharam separadamente:

- `Safe system and boundary tests`: testes reais da API retornaram exit code 1.
- `Authenticated regression tests`: testes autenticados retornaram exit code 1.

Essas falhas nao foram causadas pela submissao do experimento 001 e precisam ser
tratadas como suites independentes.

Tambem ocorreu uma falha no workflow de push `36966544861` porque ele tentou
executar testes gerais sem possuir os artefatos do prompt. O filtro do job Wiki
foi corrigido para executar somente quando:

- o evento for `workflow_dispatch`;
- `inputs.run_prompt == true`;
- o job `prompt-e2e` for executado.

## Proximo Passo Tecnico

O proximo desenho recomendado e tratar TAO como servico assincrono, nao como uma
chamada longa controlada por um turno do LLM:

- adicionar uma tool MCP `tao_wait_for_job(job_id, timeout_seconds, poll_seconds)`;
- fazer o polling internamente no MCP;
- permitir varios jobs simultaneos com IDs independentes;
- persistir estado de cada pipeline;
- remover o cancelamento global por branch;
- usar grupo de concorrencia por experimento;
- publicar somente quando o pipeline estiver terminal;
- publicar relatorio final mesmo quando o TAO terminar com erro terminal;
- nunca publicar estado `Pending` ou `Started` como resultado final.
