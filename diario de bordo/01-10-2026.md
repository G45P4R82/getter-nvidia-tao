## Contexto Inicial

O projeto começou como um repositório vazio. A primeira decisão foi não
reimplementar a API do NVIDIA TAO. O serviço oficial escolhido foi o TAO
Finetuning Microservice (FTMS), distribuído pela NVIDIA em um bundle Docker
Compose no repositório `NVIDIA-TAO/tao-tutorials`.

O repositório deste projeto passou a funcionar como um wrapper operacional do
FTMS oficial, mantendo a execução e os containers da NVIDIA, mas adicionando:

- Bootstrap reproduzível.
- Configuração local.
- Ansible.
- Testes reais.
- Integração FastMCP.
- Integração OpenCode.
- Relatórios de experimentos.

## Problema de Autenticação

Os primeiros testes identificaram que endpoints protegidos retornavam `200`
sem JWT e também com Bearer token inválido.

Exemplos inicialmente observados:

```text
GET /api/v2/orgs/getter/workspaces              -> 200 sem token
GET /api/v2/orgs/getter/workspaces              -> 200 com token inválido
GET /api/v2/orgs/%2e%2e/workspaces              -> 200
```

### Causa

O código oficial do FTMS registra o `before_request` dentro do blueprint de
autenticação. Esse hook não protege automaticamente os outros blueprints, como
workspaces, datasets e jobs.

### Correção

Foi aplicado um perímetro de autenticação no NGINX:

- `auth_request /_tao_auth` para as rotas `/api/`.
- Subrequest interno para `/api/v2/auth`.
- Encaminhamento do header `Authorization`.
- Encaminhamento de `X-Original-Url`.
- Encaminhamento de `X-Original-Method`.
- Login liberado sem JWT.
- Health liberado sem JWT.
- ReDoc liberado sem JWT.
- OpenAPI liberado sem JWT.
- Path traversal rejeitado antes do proxy.
- `INGRESSENABLED=true` passado para o FTMS.

Resultado final:

```text
health=200
no_auth=401
bad_token=401
traversal=401
```

O traversal retorna `401` porque o perímetro de autenticação é executado antes
do roteamento; continua sendo uma rejeição segura.

## Segurança de Recriação

- `docker compose down` global.
